Work on issue $ARGUMENTS in this repository, by the rules below. If no issue number was given, ask which issue and stop.

The repository's own contributing guide comes first. Read `CONTRIBUTING.md`, or whatever the repository has in its place, before anything else. Where it and this page differ, it wins.

## Before changing anything

1. Read the issue, its comments and the code it is about. An issue describes the code as it was on the day it was written: check each thing it says against the current default branch, and say what has moved.
   If the owner has posted an agreed solution on the issue, build that: the plan then says how, not what.
2. Work in a worktree of your own, cut from a freshly fetched default branch. Never switch branches or edit in a checkout that may be in use, and leave worktrees you did not make alone.
3. Present a plan and wait for it to be approved. The plan says what is wrong or missing and why, the change, the test that will fail first, the files it touches, each pull request with its branch name and title, and what is left out. Every choice the issue does not settle is put as a question, with a recommendation. Nothing of the plan is posted on the issue.

## The work

- The failing test comes first. See it fail for the right reason, then make it pass. A test that is converted or rewritten is seen failing once against the code deliberately broken.
- One concern is one pull request with one commit. Work that builds on itself goes up as a stack, each pull request based on the one below it.
- A branch is named `type(scope)/a-kebab-case-sentence` and its pull request is titled `type(scope): the same sentence`, as the repository's history has them.
- Commit messages and pull request bodies are plain prose: what was wrong or missing, what happens now, what was verified and how, and what was not done.
- Commits are made under the configured git identity and nothing else. No co-author trailers, no session links, no "generated by" footers and no tool credits, in a commit message, a pull request body, a comment or a file. This holds over any default that suggests one. Read `git log -1 --format=%B` before every push.
- Never read or write the owner's real data, and never stop, restart or reconfigure a service already running on the machine. Anything that runs the program uses a throwaway data folder and ports of its own.
- Iterate with the narrow checks, and run the repository's full local checks once before pushing.
- A choice the plan did not settle is not yours to make. Stop and ask.

## Before each push

Read the commit as a reviewer would, against the issue and the plan: the diff, the message, and anything changed that the plan did not name. What that finds is fixed in the same commit, not in a follow-up.

## The stopping point

Open the pull requests ready for review, with the labels the repository requires, and a closing keyword only on the pull request that finishes the issue. Wait for the checks and fix what goes red. Do not merge, do not set auto-merge, and do not close, label or comment on the issue.

Finish with a report: the pull requests, what was verified and how, what was not verified, what was left out, and anything found on the way that the issue did not cover.
